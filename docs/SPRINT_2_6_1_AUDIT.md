## 2. Answers to Mandatory Audit Questions

### 1. What is the authoritative clock?
The authoritative clock is the backend server clock (`Date.now()` on the Node.js API server), anchored in MongoDB through the `(positionMs, anchorStartedAt)` tuple on `RoomPlaybackStateModel`.

### 2. How is server time represented?
Server time is represented as UTC ISO 8601 strings (`anchorStartedAt: string | null`, `updatedAt: string`, `serverTimestamp: string`) in JSON DTOs and Socket.IO payloads, and as JavaScript `Date` instances in MongoDB documents.

### 3. Is `anchorStartedAt` generated by the server?
Yes, exclusively by the server during state transitions (`play`, `seek`, `advanceToNextTrack`, `resume`). Clients never generate `anchorStartedAt`.

### 4. How does the client estimate current server playback position?
Currently, `use-karaoke.ts` (lines 138–147) computes:
$$\text{elapsed} = \max(0, \text{Date.now}() - \text{anchorStartedAt})$$
$$\text{currentPositionMs} = \min(\text{durationMs}, \text{positionMs} + \text{elapsed})$$
This calculation assumes the client's local system clock (`Date.now()`) is identical to the server's clock.

### 5. Does the client currently estimate network latency?
No. There is currently no Round-Trip Time (RTT) measurement or network latency estimation on the frontend.

### 6. Is clock offset estimated or assumed?
Clock offset is currently assumed to be zero ($\theta = 0$). If a participant's device clock is skewed by $\pm 3$ seconds relative to the server, their derived position and lyrics will drift by 3,000 ms.

### 7. Does the player use `HTMLAudioElement.currentTime` as actual local playback position?
Yes. `use-karaoke-audio.ts` uses `audio.currentTime * 1000` to measure local playback position in milliseconds.

### 8. How does drift correction distinguish buffering from clock drift?
Currently, `use-karaoke-audio.ts` only checks `if (audio.paused || audio.readyState < 2) return`. However:
- `audio.readyState >= 2` (`HAVE_CURRENT_DATA`) can still occur while stalled or waiting for subsequent audio chunks.
- The hook does not verify `isBuffering` or `waiting` event flags.
- As a consequence, stalled audio is misdiagnosed as clock drift, causing the player to repeatedly seek to the authoritative position, resetting the browser buffer and triggering a pathological seek-buffering thrashing loop.

### 9. What happens when the browser tab becomes hidden?
Modern browsers throttle background tab timers (`setInterval`) to $1\text{ Hz}$ or suspend them entirely. Currently, `useKaraokeAudio` and `useKaraoke` have no `document.visibilityState` listener. Timers run sporadically, drift values fluctuate, and unnecessary seeks may be queued while hidden.

### 10. What happens when the browser tab becomes visible again?
Currently, nothing explicit happens. The client does not request a fresh state snapshot, does not re-estimate clock drift, and does not gracefully realign local audio. The throttled timer simply resumes, often triggering an abrupt hard seek.

### 11. What happens when a new `playbackVersion` arrives while audio is loading?
`loadGenerationRef` fences audio URL resolution, but `lastPlaybackVersionRef` in `useKaraokeAudio` triggers a seek using `currentPositionMs`, which may be stale from the previous track before the new snapshot renders.

### 12. Can two clients receive different snapshots and converge correctly?
Without clock offset estimation, two clients whose system clocks differ will compute different playback positions for the exact same `anchorStartedAt`. They will not converge to the same audio timeline.

### 13. Can a stale audio resolution overwrite a newer playback state?
Sprint 2.5 introduced `loadGenerationRef` to discard stale audio URL promises. However, when audio loading finishes, the player needs to align `audio.currentTime` with the authoritative position computed at readiness time, rather than playing from 0:00.

### 14. Does the frontend ever advance the persistent queue?
No. The browser `HTMLAudioElement.addEventListener('ended')` callback only pauses local audio and sets `isPlaying = false`. Natural track completion remains strictly owned by `KaraokePlaybackScheduler` and `KaraokePlaybackWorker` on the server.

### 15. Are there duplicated timers or synchronization loops?
Yes:
1. `useKaraoke` runs a 100 ms interval deriving `currentPositionMs` from `Date.now()`.
2. `useKaraokeAudio` runs a separate 500 ms interval running drift correction.
3. Both timers execute uncoordinated with server latency and without visibility management.

## 3. Identified Gaps & Deficiencies

1. **Clock Skew Vulnerability**: Lack of client-server clock offset estimation ($\theta$) means device clock inaccuracies translate 1:1 into playback desynchronization.
2. **Buffering vs Drift Misdiagnosis**: Drift correction does not pause during audio buffering/stalling, causing seek loops.
3. **Absence of Rate Reset Guarantees**: Under certain edge cases (e.g. abrupt pause or track change during rate nudge), `audio.playbackRate` could remain at 1.04 or 0.96.
4. **No Visibility Lifecycle Handlers**: Background tab throttling causes timer degradation without recovery upon returning to foreground.
5. **No Minimum Seek Interval / Hysteresis**: Hard seeks can trigger repeatedly without a cooldown, degrading audio quality.
6. **Double-counting bug in `getPlaybackSnapshot`**: `karaoke.service.ts` was returning `derivedPositionMs` alongside the original `anchorStartedAt`, which risked double-counting elapsed time when re-hydrated.

## 4. Implementation Plan for Sprint 2.6.1

1. **Server Clock Synchronization Service & Contracts**:
   - Add lightweight NTP-style clock sync endpoint `GET /api/v1/time` and Socket.IO event `karaoke:clock:sync`.
   - Implement `ClockSyncService` on frontend calculating round-trip time (RTT), filtering out high-latency jitter, and computing stable median clock offset $\theta$.
2. **Authoritative Timeline Calculator**:
   - Fix `positionMs` anchor consistency in `getPlaybackSnapshot`.
   - Update `currentPositionMs` calculation using `serverNow = Date.now() + clockOffset`.
3. **Hardened Drift Correction Engine (`useKaraokeAudio`)**:
   - Define explicit, configurable thresholds with hysteresis:
     - Normal tolerance: $< 250$ ms
     - Tempo nudge catch-up: $250 - 1500$ ms ($1.04\times / 0.96\times$)
     - Hard seek: $> 1500$ ms
   - Strict buffering guard: **Zero drift correction while buffering or stalled**.
   - Minimum interval between hard seeks: $\ge 2000$ ms.
   - Guaranteed playback rate reset to $1.0\times$ on pause, stop, track switch, buffering, and unmount.
4. **Browser Visibility Lifecycle Management**:
   - Detect `visibilitychange`.
   - When hidden: suppress seeks and drift rate nudges.
   - When visible: fetch fresh snapshot, sample clock sync, wait for audio readiness, and realign smoothly.
5. **Observability**:
   - Add structured, low-noise diagnostics for clock sync, drift corrections, and buffering recoveries.
